# InfiniteQ v0.2 Architecture

## Overview

Version 0.2 introduces major enhancements to transform InfiniteQ from a single-threaded interview into a multi-dimensional planning system with profiles, parallel threads, reflection pulses, and execution bundles.

## Key New Features

### 1. Threads & Modes

**Threads** enable parallel exploration of different aspects of a project:
- `kickoff`: Broad initial coverage
- `architecture`: Technical design
- `product_ux`: User experience and features
- `data_ml`: Data and ML architecture
- `ops_infra`: Operations and infrastructure
- `risk`: Risk analysis
- `gtm`: Go-to-market strategy
- `sanity_check`: Review existing plans
- `custom`: User-defined threads

**Modes** are entry points that configure the initial interview:
- **Kickoff Mode**: Creates a general kickoff thread for broad coverage
- **Deep Dive Mode**: Focuses on a specific aspect with deep questions
- **Sanity Check Mode**: Reviews and validates an existing plan

### 2. Project & Persona Profiles

**Project Profile** (`ProjectProfile`):
```python
{
    "type": "saas" | "internal_tool" | "game" | etc.,
    "sophistication": "toy" | "mvp" | "production",
    "team_size": "solo" | "2-3" | "4-10" | "10+",
    "tech_constraints": ["must_be_js_ts", ...],
    "timeline": "weekend" | "1-4_weeks" | etc.,
    "budget_band": "<1k" | "1k-10k" | etc.,
    "non_goals": ["avoid_ml", ...]
}
```

**Persona Profile** (`PersonaProfile`):
```python
{
    "role": "founder_technical" | "tech_lead" | "pm" | etc.,
    "comfort_with_tech": "low" | "medium" | "high",
    "comfort_with_business": "low" | "medium" | "high",
    "preferred_depth": "light" | "balanced" | "deep"
}
```

These profiles contextualize every question and response.

### 3. Phase Coverage

Projects are tracked across lifecycle phases:
- `prototype`: v0 / proof of concept
- `v1`: First real launch
- `scale_up`: Growing user base
- `v2_plus`: Mature product

Coverage is now 2D: **Dimension × Phase**

Example dimensions:
- problem, users, constraints, features
- architecture, data_ml, operations
- risks, gtm (go-to-market)

### 4. Reflection Pulses

Every 5-10 questions (random), the system injects a reflection question:
> "In your own words, what tricky nuance are we missing in this {thread.type} thread?"

User responses become **PlanNotes**:
```python
{
    "id": "...",
    "thread_id": "...",
    "raw": "User's freeform reflection",
    "distilled": "LLM summary",
    "tags": ["constraint:weekends_only", "risk:scope_creep"]
}
```

These notes are fed back into the Question Engine and Plan Reducer to steer subsequent questions.

### 5. Views & Sealed Sections

Plans contain **PlanChunks** with visibility controls:

```python
{
    "id": "...",
    "type": "feature" | "risk" | "assumption" | etc.,
    "content": "...",
    "visibility": "internal_only" | "team" | "stakeholder" | "deck_friendly" | "agent_only",
    "parked": false  # If true, not part of active plan
}
```

When synthesizing the final plan, select a **ViewProfile**:
- `builder`: Full technical details
- `stakeholder`: Business-focused
- `investor`: Pitch-friendly
- `agent_spec`: For AI coding tools

### 6. Execution Bundles

The Plan Synthesizer now generates:

**RepoScaffold**:
```python
{
    "language": "ts",
    "frameworks": ["fastapi", "react", "prisma"],
    "structure": {
        "backend/": ["app.py", "models/", "services/"],
        "frontend/": ["src/", "public/"]
    }
}
```

**Tasks**:
```python
{
    "id": "TASK_001",
    "title": "Set up FastAPI backend",
    "phase": "prototype",
    "description": "...",
    "acceptance_criteria": ["FastAPI runs", "Health endpoint works"],
    "estimate": "S" | "M" | "L",
    "dependencies": []
}
```

**LLM Prompts**:
```python
{
    "id": "PROMPT_001",
    "title": "Initial setup for ClaudeCode",
    "target": "claudecode",
    "prompt": "Please set up a FastAPI backend with..."
}
```

Complete bundle structure:
```python
{
    "repo_scaffold": {...},
    "tasks": [{...}, ...],
    "prompts": [{...}, ...]
}
```

## Data Model Changes

### SessionData (v0.2)

```python
class SessionData(BaseModel):
    session_id: str
    idea_brief: IdeaBrief
    plan_state: PlanState
    coverage: CoverageMap  # Global across threads
    qa_history: List[QAPair]  # Legacy

    # NEW in v0.2
    project_profile: ProjectProfile
    persona_profile: PersonaProfile
    threads: Dict[str, ThreadState]  # Keyed by thread_id
    active_thread_id: Optional[str]
    mode: Mode
    plan_chunks: List[PlanChunk]

    created_at: str
    updated_at: str
    completed: bool
```

### ThreadState (NEW)

```python
class ThreadState(BaseModel):
    id: str
    session_id: str
    type: ThreadType
    title: str
    root_prompt: str
    coverage: CoverageMap  # Per-thread coverage
    phase_coverage: PhaseCoverageMap  # Coverage by phase
    questions_asked: int
    questions_since_reflection: int
    qa_history: List[QAPair]
    notes: List[PlanNote]
    created_at: str
    last_updated: str
    active: bool
```

## API Changes

### Session Creation (Updated)

**POST /api/v1/session**

Request:
```json
{
    "idea": "A SaaS tool for...",
    "mode": "kickoff",
    "project_profile": {
        "type": "saas",
        "sophistication": "mvp",
        ...
    },
    "persona_profile": {
        "role": "founder_technical",
        ...
    }
}
```

Response:
```json
{
    "session_id": "...",
    "thread_id": "...",  # Initial thread
    "first_questions": [...],
    "coverage": {...},
    "project_profile": {...},
    "persona_profile": {...}
}
```

### Thread Management (NEW)

**POST /api/v1/session/{id}/threads**
Create a new thread

**GET /api/v1/session/{id}/threads**
List all threads

**PATCH /api/v1/session/{id}/threads/{tid}**
Update thread (rename, activate/deactivate)

**POST /api/v1/session/{id}/threads/{tid}/answer**
Submit answers to a thread

Response includes:
```json
{
    "next_questions": [...],
    "thread_coverage": {...},
    "phase_coverage": {...},
    "global_coverage": {...},
    "reflection_prompt": {...}  # If it's time for reflection
}
```

### Finish with Views (Updated)

**POST /api/v1/session/{id}/finish**

Request:
```json
{
    "view_profile": "builder",
    "include_execution_bundle": true
}
```

Response:
```json
{
    "json_plan": {...},
    "markdown_brief": "...",
    "execution_bundle": {
        "repo_scaffold": {...},
        "tasks": [...],
        "prompts": [...]
    },
    "plan_chunks": [...]
}
```

## Services Architecture

### SessionManager (Updated)

New methods:
- `create_session()` - Now accepts profiles and mode
- `create_thread()` - Create additional threads
- `get_thread()` - Retrieve thread by ID
- `set_active_thread()` - Switch active thread
- `update_thread()` - Update thread metadata
- `update_thread_after_answers()` - Update thread with Q&A
- `should_inject_reflection()` - Check if reflection needed
- `add_plan_note()` - Add reflection note to thread
- `list_threads()` - List all threads in session

### QuestionEngine (To Update)

Enhanced to accept:
- `project_profile` and `persona_profile` for context
- `thread_state` for thread-specific questions
- `plan_notes` to incorporate reflections
- `phase_coverage` to target weak phases

Returns questions with:
- `phase` field (which lifecycle phase)
- `kind` field ("multiple_choice" or "reflection")

### PlanReducer (To Update)

Enhanced to:
- Accept `thread_id` for thread-specific updates
- Process `plan_notes` from reflections
- Update both `coverage` and `phase_coverage`
- Consider `project_profile` and `persona_profile`

### PlanSynthesizer (To Update)

Enhanced to:
- Accept `view_profile` to filter visibility
- Generate `execution_bundle`:
  - Repo scaffold based on tech constraints
  - Task breakdown by phase
  - Ready-to-use prompts for Cursor/ClaudeCode
- Filter `plan_chunks` by visibility for the view

## Migration from v0.1

v0.1 sessions can coexist with v0.2:
- Old sessions without threads continue to work (legacy mode)
- New sessions automatically create an initial thread
- All v0.1 endpoints remain backwards compatible

Default behavior:
- No profiles provided → use defaults
- Single thread (kickoff) created automatically
- Phase coverage starts at 0% across all phases

## Benefits of v0.2

1. **Parallel Exploration**: Multiple threads allow deep dives into specific areas without losing breadth
2. **Contextual Questions**: Profiles ensure questions match the user's skill level and project constraints
3. **Reflection Integration**: Periodic reflections capture nuances that structured Q&A might miss
4. **Lifecycle Awareness**: Phase coverage ensures planning addresses MVP, launch, and scale concerns
5. **Audience-Specific Views**: Same plan can be presented differently to builders, stakeholders, and investors
6. **Execution Ready**: Bundles provide immediate actionable artifacts (scaffolds, tasks, prompts)

## Example Workflow

1. **Start Session**:
   ```
   User provides idea + profiles
   → System creates session with kickoff thread
   → Asks initial broad questions
   ```

2. **Kickoff Thread** (Questions 1-15):
   ```
   Covers all dimensions at 20-40%
   User chooses Reflection: "We need this done in 2 weekends"
   → System tags: constraint:time_tight
   ```

3. **Create Architecture Thread**:
   ```
   User: "Deep dive on architecture"
   → System creates architecture thread
   → Focuses on tech stack, deployment, scaling
   → Uses project_profile.tech_constraints
   → Asks phase-specific questions (v0 vs v1)
   ```

4. **Create Risk Thread**:
   ```
   User: "What could go wrong?"
   → System creates risk thread
   → Analyzes constraints, schedule, team size
   → Proposes mitigation strategies
   ```

5. **Finish**:
   ```
   User selects "Agent Spec" view
   → System synthesizes:
     - Filtered plan (only agent-relevant sections)
     - Repo scaffold (FastAPI + React structure)
     - Task breakdown by phase
     - Ready prompts for ClaudeCode
   ```
